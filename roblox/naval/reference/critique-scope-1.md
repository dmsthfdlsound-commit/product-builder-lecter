# 적대적 검증: 1인 생산 현실성 (1차)

> 1인(+AI) 생산 현실성 · 출하 가능성 렌즈. 실측 기준선: 이 레포의 직전 프로젝트는 실제로 978줄(서버 668 + 클라 310), 단일 스크립트, 권위 로직 1개이고, 커밋 로그상 게임 코드는 2026-08-02~08-03 이틀에 작성됐다. 즉 이 문서는 "라이브 게임을 단 하루도 운영해본 적 없는 상태에서 쓰인 7개월 미드코어 계획"이며, 직전 계획서의 "7일 비공개 / 14일 공개 출시"도 실행 증거가 없다(roblox/naval/은 빈 디렉터리). 판정: 문서의 자기 인식·리스크 선처리·거절 표는 내가 본 1인 계획서 상위 5%지만, 캘린더는 3~5배 낙관이고 v1 정의는 출하 가능한 최소체의 약 4배다. ▶ 단일 최다 실패 원인: "게이트 실패로 죽는 것"이 아니라 W12~20 사이에 P2가 여전히 미완인 상태로 표류하는 것 — 5개월간 외부 플레이어가 0명이므로 도파민 공급원(문서의 DDD 4원칙 = 유저 숫자)이 끊기고, 킬 크라이테리아는 전부 "게이트에 도달했을 때"만 발동하므로 도달하지 못하는 방식의 죽음에는 아무 방어선이 없다. ▶ 최소 재구조화(이 3개만 해도 살아남는다): ① v1을 3단 공개 출시 사다리(v0.1 항해 → v0.5 함포 → v1.0 약탈)로 쪼개 W6~10에 실제 공개 출시하고 그 뒤 모든 단계를 "라이브 게임 업데이트"로 전환한다. ② 보딩 = L3 컷신으로 선결정해 W0의 설계 분기를 제거한다. ③ 시간 기반 트립와이어("단계가 예정의 1.5배를 넘기면 일정이 아니라 기능을 자른다", "누적 200시간 내 공개 출시 없으면 아레나 피벗 자동 발동")를 추가한다.

## 🚫 캘린더가 3~5배 낙관 (30주/450시간 ← 실제 필요 1,200~2,250시간). v1 정의를 그대로 두면 어떤 일정 관리로도 출하되지 않는다.
**실패 시나리오**: 주 15시간 × 30주 = 450시간 안에 14,000~22,000줄의 '서버 권위 + 모바일 성능 제약' Luau, 독립 시스템 26개, 파이프라인 툴, 외주 에셋, 라이브옵스를 전부 넣었다. 실증 속도는 978줄/단일 스크립트/권위 1개(=Luau 중 가장 싼 종류)이고, 네트워크·복제·실기기 튜닝 코드는 줄당 소요가 5~10배다. 18k줄 × 순증 8~15줄/시간(디버깅·실기기 왕복·밸런스 포함) = 1,200~2,250시간 = 주 15시간이면 80~150주. W0 자체가 이미 반례다: S1(키네마틱 선체 + 해석 Gerstner + 20Hz 서버 복제 + 클라 보간 + 고스트 렌더 + 16척 + 250ms 지연)이 2세션(4시간), S5(4기어 + 기어별 카메라 + 비대칭 램프 + 오디오 + 승무원 8명 5상태 애니메이션 + 수평선 실루엣 6척 + 파도)가 1세션(2시간)으로 잡혀 있다. 승무원 5상태 애니메이션 리깅/소싱만 2~4세션이다. 실제 W0은 1주가 아니라 4~8주. 게다가 주 15시간을 30주 무결근으로 가정해 병가·의욕 저하·본업 크런치·로블록스 플랫폼 변경 대응의 슬랙이 0이다(현실 실현율 60~70% → 450시간은 실질 300시간).

**처방**: '고정 스코프 · 고정 날짜'를 '고정 시간 예산 · 가변 스코프'로 뒤집고 v1을 3단 공개 출시 사다리로 쪼갠다. ▸v0.1 «항해»(누적 80~120h, 7~10주, 실제 공개 출시): 슬루프 1척, 4기어 + 기어 연동 카메라, Gerstner 파도, 승무원 4~6명 3상태, 수평선 실루엣 LOD, 리깅/바람 오디오 2레이어, 미니맵+나침반, 세이브 v0, 모바일 5버튼. 전투 코드 0줄. ▸v0.5 «함포»(누적 250~350h): 브로드사이드 + 스위벨, 약점 팝, 브레이스/퍼펙트 브레이스, 스쿠너 1종 AI 4상태, 격침→코인, 무기 업그레이드 3단, 수리, 항구 1곳(반경 진입 = 전체화면 메뉴). ▸v1.0 «약탈»(누적 450~600h): 보딩 컷신 + 4버튼 보상 메뉴, 승무원 경제, 로그 웨이브 1종, 세그먼트 래칫, 샨티 1곡 + 전투 덕킹, 코스메틱 상점, 손실 보험. ▸그 뒤에는 로드맵이 아니라 라이브 지표가 다음 업데이트를 정한다(P3~P6 간트 삭제). 정직한 환산: 문서가 확보한 450시간으로 실제로 살 수 있는 것은 문서의 v1이 아니라 이 사다리의 v0.5다. 이 문장을 문서 맨 앞에 박아라.

## 🚫 최대 리스크(‘아무도 클릭하지 않는다’)를 5개월간 방치한다. 재미 리스크는 W0에 회수하는데 시장 리스크는 W17 소프트런치까지 미검증이다.
**실패 시나리오**: 로블록스에서 미드코어 해상 장르가 죽는 실제 경로는 '재미없음'이 아니라 '발견 실패'다 — 알고리즘은 썸네일 CTR과 초반 리텐션에만 반응하고(문서 P5가 스스로 인정), 오디언스는 문서가 상정한 미드코어보다 어리고 즉시 이해되는 루프를 선호한다. CTR·첫 1분 이탈은 항해 토이 하나로 지금 살 수 있는 정보인데, 계획은 26주치 코드를 만든 뒤에 확인한다. W17에 CTR이 나쁘면 회수 불가한 5개월이 매몰비용이 되고, 문서의 킬 크라이테리아 4개 중 이 실패를 잡는 조항은 하나도 없다. 부가 피해: 5개월간 외부 반응 0 → DDD 4원칙(진짜 도파민은 유저 숫자)이 작동하지 않아 번아웃 타이머가 먼저 터진다. 그리고 P3의 전제인 '알파 테스터 30~60명'을 어디서 데려올지도 답이 없다(모집 자체가 별도 마케팅 프로젝트).

**처방**: v0.1 항해 토이를 프로토타입이 아니라 실제 공개 경험으로 출시한다(W6~10, 무료, 썸네일 2종 A/B, 설명·태그 최적화 포함). 측정 항목 4개만: 썸네일 CTR, 첫 60초 이탈률, 평균 세션, 저가 안드로이드 p50 fps. 이 출시가 동시에 (a) 시장 리스크 회수 (b) 알파 테스터 풀 자동 확보 (c) P5의 썸네일 A/B 학습을 6개월 앞당김 (d) 라이브 운영 근육 습득 — 이 개발자가 아직 한 번도 안 해본 것 — 을 전부 해결한다. 트레이드오프는 '완성 안 된 걸 내는 부끄러움' 하나뿐이고, 그건 비용이 아니다.

## 🚫 보딩(S2)이 W0 종료 후에도 설계 분기(fork)로 남아 P2 백로그를 고정할 수 없다. 그리고 L1/L2 중 무엇을 통과하든 v1에서 가장 비싼 시스템이다.
**실패 시나리오**: 플로차트는 S2 결과에 따라 GO/GO2/GO3 세 갈래를 만들고, 그 결과가 P2 예산(6주 중 1.5주), 항구 하선 방식, P6 코업 스테이션, §7 '걸어다니는 선내'까지 전부 규정한다. 분기를 남긴 채 W1에 진입하면 §7 트립와이어 4('기능 추가는 삭제 후보 동반')와 W4-5의 '§2 목록 고정, 추가 금지'가 자기모순이 된다 — 고정할 목록이 아직 없다. 게다가 L1/L2는 이동 갑판 캐릭터 컨트롤 + 네트워크 소유권 전환 + 승무원 근접전 + 아레나 인스턴싱 + 카메라 전환 + 보상 메뉴 = 사실상 두 번째 게임이고, W0에서 '60초 × 4인 × 10회 관통 0건'을 통과해도 실제 콘텐츠가 올라간 뒤 desync 버그세가 모든 후속 단계에 재발한다(로블록스 이동 플랫폼 위 휴머노이드는 통과가 아니라 관리 대상이다).

**처방**: v1 보딩 = L3(6초 컷신 + 4버튼 보상 메뉴)로 **선결정**하고 분기를 제거한다. S2 스파이크를 '3안 30분씩 비교'에서 '컷신 + 보상 메뉴 연출이 감정적으로 먹히는가' 1세션으로 교체(로프 스윙 연출 + 승무원 함성 + 메뉴 등장 타이밍만 튜닝). 절약된 시간은 문서가 이미 말한 대로 보상 메뉴와 승무원 연출에 재투자. L1/L2 실아바타 보딩은 '라이브 게임 D7 ≥ 12% + 개발자 2명 이상'을 조건으로 §7 거절 표로 이동. 부수 효과: P6의 2인 동승 스테이션 근거(S2 재사용)가 사라지므로 그것도 자동으로 로드맵에서 빠진다.

## 🚫 라이브옵스 케이던스(6주 시즌 영구 반복 + 유료 시즌 패스)는 1인이 지속 불가능하다. 여기가 번아웃의 실제 발화점이다.
**실패 시나리오**: 플레이어가 생기는 순간 모더레이션, 버그 트리아지, 디스코드 응대, 밸런스 조정, 핫픽스가 상시 주 5~10시간을 점유한다. 주 15시간 중 실제 개발 예산은 5~10시간으로 줄어든다. 그 예산으로 P6은 시즌패스 + 전설선 2척 + 서버 전체 이벤트 + 공유 킬피드 + 길드 함대 + 2인 동승 스테이션을 4주에 만들라고 요구하며, 이후 6주 주기로 무한 반복한다. 특히 유료 시즌 패스는 기한·환불·기대치가 붙는 납기 계약이다 — 미달 시 코드가 아니라 평점과 신뢰가 먼저 무너지고, '쉬면 매출이 죽는' 구조가 만들어져 첫 감기에 프로젝트가 멈춘다. 문서의 다른 모든 곳에는 폴백이 있는데 라이브옵스에만 폴백이 없다.

**처방**: 1년차에 유료 시즌 패스 금지. 대체: (a) 준비되면 내는 코스메틱 드롭(날짜 약속 없음, 조합 테이블로 0.5세션짜리) (b) 주기 리셋 리더보드 + 기존 에셋 재조합 배지로 '시즌'의 체감 90%를 신규 에셋 0으로 확보 (c) 로드맵에 '라이브 운영 주 6시간'을 명시적 고정 비용으로 계상하고 개발 예산을 주 15h가 아니라 주 9h로 재계산(캘린더 전체 ×1.6). (d) 휴가 프로토콜을 미리 문서화: 2주간 아무 업데이트 없어도 게임이 안 죽는 구조(시즌 없음, 기한 없음)가 1인 라이브 게임의 유일한 생존 형태다.

## 🚫 콘텐츠 파이프라인(ShipBuilder Studio 플러그인 + 런타임 조립 + 부착점 자동 배치 + 팔레트/데칼)이 'P3 시작 전 준비'로 숨겨진 3~6주 도구 개발이다.
**실패 시나리오**: §6은 '새 클래스 = 테이블 한 블록 = 1세션'이라고 하지만 그건 툴이 완성된 뒤의 단가이고, 툴 자체의 개발·디버깅·유지 비용은 어디에도 계상되지 않았다. 데이터로 배를 조립해 보기 좋은 결과를 내는 어셈블러(스케일 × 마스트 킷 × 건포트 자동 배치 × 약점 어태치먼트 × 팔레트)는 미리보기 플러그인과 런타임 경로 이중 구현까지 포함해 실측 3~6주다. 그리고 v1에 필요한 선체는 3~4종뿐이다 — 손으로 3번 만드는 것이 툴을 만드는 것보다 압도적으로 싸다. 이건 '파이프라인 없으면 배 1척에 1주'라는 정당화가 거꾸로 적용된 전형적인 1인 개발 함정(툴을 만드느라 게임을 못 만든다)이다.

**처방**: v1에서 ShipBuilderPlugin 삭제. ShipSpec 테이블 + 런타임 조립 최소본만 남기고, 부착점은 손으로 배치한 프리팹 3개(슬루프/브릭/프리깃)로 고정. 코스메틱 조합 테이블(1에셋 → 8 SKU)은 유지 — 이건 진짜로 싸고 ROI가 높다. 항구 12조각 모듈 킷도 v1에서는 불필요(항구 1곳은 손으로 짜는 게 싸다). 파이프라인 툴의 발동 조건을 수치로 못 박아 §7 표에 넣어라: '선체 5종 이상 또는 항구 3곳 이상이 실제로 필요해진 시점'.

## 🚫 성능 예산에서 승무원(애니메이션 휴머노이드)이 빠져 있다. W0의 S3 PASS가 허위 통과가 될 구조다.
**실패 시나리오**: S3 지옥 서버는 AI 12척(원거리 8척은 단일 파트 실루엣) + 포탄 200발 + 봇 8명만 측정한다. 그런데 이 게임의 정체성은 문서 스스로 강조한 '파티클이 아니라 승무원'이며 P1/VS는 근거리 선박마다 8~14명 × 5상태 애니메이션 리그를 요구한다. 저가 안드로이드(A14/A23급)에서 실제 프레임 킬러는 레이캐스트 포탄이 아니라 근거리 4~6척 × 10 애니메이션 리그 + Terrain Water + Gerstner 코스메틱 변형 + 포말/스프레이 파티클이다. 빈 씬으로 W0에 45fps를 받고 W10에 실제 콘텐츠로 30fps 아래로 떨어지면, 그때는 아키텍처를 되돌릴 시간이 없다 — 그리고 이 계획의 킬 크라이테리아 3번(6척 교전 30fps 미달 → 아레나 피벗)이 6개월 뒤에 발동한다는 최악의 시나리오가 된다.

**처방**: S3 스펙에 '근거리 6척 × 승무원 10명 애니메이션 + 항구 1곳 스트리밍 로드'를 추가하고, 대조군으로 승무원 0명 버전을 함께 재서 승무원의 ms 단가를 숫자로 확정한다. 승무원 폴백을 미리 명시: 10명 → 4명 / 거리 기반 리그 컬링(150 studs 초과는 애니메이션 정지, 250 studs 초과는 정적 파트) / 아바타 리그 대신 단순 메시 + 트윈. 그리고 기능별 ms·MB 원장(perf budget ledger)을 문서화해 금요일 실기기 테스트에서 초과 항목을 자동 강등한다 — 지금은 측정 시점만 있고 예산 배분표가 없어서 초과 원인 추적이 불가능하다.

## 🚫 킬 크라이테리아가 전부 '게이트에 도달했을 때'만 작동한다. 게이트에 영원히 도달하지 못하는 방식의 죽음에는 방어선이 0이다.
**실패 시나리오**: 4개 조항 모두 테스트 결과 조건부다(3분 핸들 재실패, 보딩 완료율, fps, 재플레이 의향). 그러나 1인 개발의 실제 사망 원인은 '게이트 실패'가 아니라 'P2가 6주 예정인데 14주째 진행 중'이며, 이 상태를 강제 종료하는 규칙이 문서에 없다. 오히려 §5 게이트 운용 규칙 ③('게이트 미달로 인한 연기는 실패가 아니다')이 무한 연기를 정당화하는 조항으로 오용될 수 있다. 게다가 모든 게이트가 외부 인력을 전제한다 — 테스터 7명(W0), 8명(W10), 알파 30~60명(W11), 인플루언서 5명(W23) — 모집·일정 조율 비용이 0으로 가정되어 있어, 사람을 못 모으면 판정 자체가 미뤄지고 미룸이 정당해진다. 이것이 데스마치의 정확한 발생 기전이다.

**처방**: 시간 기반 트립와이어 3개를 §7에 추가한다. ① 어떤 단계가 예정 기간의 1.5배를 넘기면 남은 기능을 잘라내고 그 자리에서 종료 게이트를 실시한다 — 일정 연기 금지, 스코프만 절단(W10이 오면 VS 목록이 잘리고 날짜는 안 밀린다). ② 누적 200시간 안에 공개 출시가 없으면 §2-3의 아레나 피벗(400×400 고정 투기장 함포전)을 자동 발동한다. ③ 테스터 축소 프로토콜을 명시한다: 최소 3명 + 공개 빌드 지표로 대체 판정 가능, 모집 실패는 게이트 연기 사유가 아니다. 추가로 §5 규칙 ③을 '연기는 1회, 최대 2주까지만 실패가 아니다'로 좁혀라.

## 🚫 외주 리드타임과 현금이 크리티컬 패스에 무계획으로 들어 있다.
**실패 시나리오**: 선체 메시 $300~800, 샨티 3곡 $450~1,200, 썸네일/아이콘 $100~300, 실기기 2대, 잠재 광고비 = 총 $1,000~2,500이 예산 항목으로 존재하지 않고, 자금 계획도 없다. 더 위험한 것은 리드타임이다: 발주 → 초안 → 수정 → 납품이 2~4주이고 수정 라운드가 붙으면 더 길다. 그런데 P1(W1~W4)은 승무원 애니메이션·샨티·선체 메시에 의존한다. 벤더 대기로 세션이 멈추면 가장 먼저 깨지는 것이 DDD 1원칙(매 세션 클립)이고, 동기 구조가 무너지는 것이 코드 지연보다 치명적이다.

**처방**: W0 1일차에 선체 1종 + 샨티 1곡만 발주한다(3곡 아님). 납품 전 전 구간은 로열티프리/기본 파트 플레이스홀더로 진행하고, 어떤 세션도 벤더 납품을 선행조건으로 두지 않는다는 규칙을 명문화. 현금 상한을 문서에 박아라: 'v1 공개 출시까지 총 $800 이하, 나머지 2곡·썸네일·광고는 실제 매출이 발생한 뒤 재투자'. 또한 클립 제작 비용(세션당 15~30분 = 주 약 3시간)도 계상되지 않은 숨은 오버헤드다 — 마케팅으로 인정하고 예산에 넣거나, 클립을 주 2회로 줄여라.

## 🚫 라이브 사고 대응 능력(운영 툴킷)이 로드맵 어디에도 없다. 권위 로직 11개 + 경제 + DataStore를 공개하는데 되돌릴 수단이 없다.
**실패 시나리오**: P5의 '2시간 내 롤백 가능한 배포 파이프라인'은 코드 롤백이고, 익스플로잇 1건이 경제를 오염시켰을 때 필요한 데이터 롤백이 아니다. 문서는 안티치트를 '월 1세션 자기 공격'과 'P3 1차 감사'로만 다루는데, CCU 500에서 익스플로잇은 며칠 안에 경제를 파괴하고, 그때 계정별 그랜트/차감·데이터 버전 복구·기능별 즉시 차단이 없으면 유일한 대응은 서버를 닫는 것뿐이다. 1인 개발자에게 이건 곧 프로젝트 종료다.

**처방**: 공개 출시의 선행조건으로 '최소 운영 툴킷' 1~2주를 신규 편성한다: (a) 서버 플래그로 기능을 즉시 끄는 원격 컨피그 — 규칙화: 킬스위치 없는 신규 시스템은 출시 금지 (b) DataStore 버전/백업 기반 계정 단위 롤백 (c) 관리자 그랜트/차감/밴 커맨드 (d) 경제 이상치 알람(시간당 획득 상한 초과 로그). 이건 컷이 아니라 반드시 추가해야 하는 항목이고, 대신 §8의 GitHub Actions CI + Open Cloud 스테이징 자동 배포 예산을 여기로 옮겨라(1인 PR 워크플로에는 리뷰어가 없어 CI의 ROI가 낮다).

- ShipBuilder Studio 플러그인 → 삭제. 이유: v1에 필요한 선체는 3~4종. 손으로 3번이 툴 3~6주보다 싸다. ShipSpec 테이블 + 런타임 조립 최소본만 유지.

- 켄웨이 함대형 방치 수익 → 라이브 이후. 이유: 별도 저장 스키마 + 오프라인 시간 정산(치트 표면) + 역할 밸런스 + UI = 최소 3~4주. D7 기여는 아직 가설이고 검증 비용 < 구현 비용이 성립하지 않는다.
- 해상 계약 15종 → 3종(격침 · 약탈 · 호송). 이유: 15종은 보상 밸런스 15배가 아니라 버그 표면 15개다. 3종으로 '계약이 재접속을 만드나'를 먼저 판정.
- 유료 시즌 패스 → 1년차 금지. 이유: 기한이 붙은 납기 계약은 1인 라이브 게임의 번아웃 1번 기전. 리셋 리더보드 + 재조합 코스메틱 드롭으로 대체.

- GitHub Actions CI + Open Cloud 스테이징 자동 배포 → 로컬 stylua/selene + TestEZ 수동 실행으로 축소. 이유: 1인 PR 워크플로에 리뷰어가 없다. 절약분은 운영 툴킷(블로커 10)으로 이전하고, CI는 협업자가 생기거나 라이브 핫픽스가 실제로 필요해질 때 도입.
