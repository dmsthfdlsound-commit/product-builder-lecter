# 적대적 검증: 1인 생산 현실성 (2차)

> Production/scope reality for a SOLO first-time systems developer — calibrated against what this repo proves he has actually shipped (978 lines of Luau, 2 files, 2 days, all engine-native APIs, never published, zero retention data), not against what the document claims as its baseline.

**판정: needs-rework**

## 🚫 The core physics architecture is specified two mutually exclusive ways, and the plan 'locks' it at W2 anyway.
**실패 시나리오**: Ship doc §5.1 decides kinematic own-integration and bans the constraint stack by name: 'LinearVelocity, AngularVelocity, AlignPosition, AlignOrientation, PlaneConstraint, VectorForce 전부 미사용.' But combat doc §4.1 implements buoyancy AS VectorForce ('4~8개 샘플점의 VectorForce'), combat doc §10 lists 'our constraint stack (LinearVelocity + AlignOrientation + PlaneConstraint)', and roadmap spike S2 BUILDS the physics version ('부력 = 6개 샘플 포인트 VectorForce, 서지 = LinearVelocity') while calling kinematic the FAILURE fallback. So the ship doc's decision is the roadmap's failure state. Gate A stamps '6개월간 번복 금지' on a decision that was never made. With AI assistance this is worse, not better: the model implements whichever table it was last shown, and both get written. The doc names this exact outcome as the worst case — '6개월 뒤에 갈아타는 게 최악' — and then sets it up in week 0.

**처방**: Pick kinematic own-integration in week 0 and delete every VectorForce/LinearVelocity/AlignOrientation reference from all four documents in one editing pass. It wins on the merits once you also cut deck free-roam (see below): its stated cost is 'we write 100% of the deck-movement layer,' and one-player-per-ship with station seats means there is no deck-movement layer to write. Also delete ship doc §7's 12-week 구현 순서 table, which is a second contradictory architecture and scope plan.

## 🚫 Calendar is off by 3–5x, and every gate is indexed to a week number that will be meaningless by month two.
**실패 시나리오**: Roadmap claims 32 weeks to public launch at 12 h/week = 384 hours total. Item-by-item against a developer whose shipped output is 978 lines of engine-native Luau: S1 deterministic Gerstner + EditableMesh + LOD + parity harness is 40–80 h; S2 hull motion stability 60–120 h; S3 moving-deck controller 80–200 h and may never fully pass (the doc itself calls it '이 프로젝트에서 가장 어려운 엔지니어링'); S4 N-ships + FastCast + PartCache + proxy LOD 40–80 h; S5 boarding lock 30–60 h; tooling/PerfHUD/CI 20–30 h. P0 alone is 270–570 h — 22–48 weeks, not the allocated 3 weeks. Full path to public launch is roughly 1,200–2,100 h = 100–175 weeks at 12 h/week, i.e. 2 to 3.4 years, before any bug tail, art dependency, or the near-certain one architecture rewrite. Because all gates are written as 'at W_n' with no rule for 'it is now W_n+20 and I am still in P1,' the gate structure detaches from reality in month 2 and then never fires — the project drifts instead of stopping.

**처방**: Re-index every gate from week numbers to events and add one absolute calendar stop-loss: 'if strangers have not passed the fun gate by month 6, stop.' Multiply all phase estimates by 3 and re-derive. Also write down the actual sustainable hours honestly — the doc's own table says 6 h/week = ×2.0, which on corrected estimates is 4–6 years, and that is the number that decides whether this project is possible at all.

## 🚫 No stranger ever plays this for ~14–20 months. The only risk the plan retires early is technical; the risk that actually kills naval games is never tested.
**실패 시나리오**: Five spikes retire engine risk. Zero retire appeal risk — and the doc's own revenue section concedes appeal is the binding constraint, citing Dead Sails at 39.8M visits → 41–71 CCU and AO at 24k → 800. The fun gate (B) is 5–8 friends in a scheduled 90-minute session with the developer watching; friends will hit the '무보상 자발 플레이 median >= 8분' bar out of politeness, so that gate can pass on a game nobody wants. First public-facing build is P3 soft launch, realistically month 14–20 at corrected velocity. This is also the failure mechanism itself: the killer is not a bad decision, it is the DURATION BETWEEN FEEDBACK EVENTS. A solo unpaid developer does not sustain 1,000+ hours on self-recorded clips with no strangers and no revenue. Attrition around month 5–12 is the single most likely end state, and everything else (S3, live-ops, PvP balance) only matters if he is still there.

**처방**: Ship the P0 spike output as a real, public, tiny game at week 8–12 (~120–180 h). It is already 80% built by W0-6 of the existing plan ('폰 터치로 배를 몰아 항주 파도를 뚫는다') and it is precisely the doc's own Gate-A fallback, '1인 1함선 아케이드 해전.' Contents: ocean, one hull, sail state machine with the 6-channel feedback, roundshot with manual aim, brace with telegraph, weak-point/swivel, 3-segment HP, one enemy that telegraphs, disable state, results screen, 3 cosmetic SKUs. Read D1 from strangers. That number — not a friend playtest — is what authorizes building the RPG layer at all, and it arrives at 150 hours sunk instead of 1,000.

## 🚫 Spike timeboxes guarantee that rule 1 — the rule the doc says 'saves the project' — is the first rule broken.
**실패 시나리오**: S1 4 sessions, S2 5, S3 5, S4 4, S5 3 = 21 sessions ≈ 35 hours for work that realistically needs 270–570. Every spike will hit its timebox at 'almost working,' which is the exact psychological state in which a solo developer overrides his own auto-FAIL rule. If the rule IS honored, all five fall to fallback and Gate A's kill clause fires into the arcade scope-reduction — which is the correct destination, but the plan will read it as failure rather than as the plan working.

**처방**: Write the response to '80% done at the timebox' now, in advance, in one sentence: take the fallback. And since honoring the rule lands on the arcade version anyway, skip the theater — adopt the arcade scope in week 0 as the plan, not as the loss condition.

## 🚫 S3 (walking on a moving deck) sits on the critical path but is a permanent tax, not a one-time spike — and the doc already says its fallback may be better.
**실패 시나리오**: It is not one spike; every later feature re-touches it: boarding, stations, crew NPCs, interiors, ramps, respawn, ragdoll, edge cases under lag, plus hand-authored invisible collision boxes (8–16 each) re-validated per hull across 7 hulls. There is no 'done.' Meanwhile the doc's own S3 fallback note concedes station seats with 1-tap switching '모바일 UX상 오히려 나은 선택일 수도 있음,' and §5.6 already names deck free movement as 스코프 컷 1순위. So the hardest, most open-ended engineering in the project is being done to deliver something the design doc suspects is worse on the primary platform, which is mobile with 5 always-on buttons.

**처방**: Delete S3 in week 0. Ship station seats plus 1-tap station switching. This removes the largest engineering risk, its permanent maintenance tax, and the main reason the kinematic architecture looked expensive — and it makes the week-0 architecture decision easy.

## 🚫 Three mutually inconsistent stat tables for the same ships and weapons across the four sections.
**실패 시나리오**: 슬루프 is 62 studs / 92 speed / 3×420 HP / 110 instances (ship §1.2) but 150 studs / 105 speed / 3×1,000 HP (roadmap slice). Player reference hull is variously 슬루프, 브릭 100 studs 3,000 HP (combat §2), and 1,200 HP total (job §2-3). Roundshot reload is 4.5s (combat §3.1) and 6.0s (job §2-3). Mortar is 220 dmg / 7.0s and 130 dmg / 12.0s. Brace is −65% and −55%. Sail transition is 2.5s and 1.2s→0.7s. These are not tuning variance; they are three separately-authored drafts never reconciled. With AI implementation this is a direct bug factory — whichever table is in context becomes the code, silently.

**처방**: One pass to produce a single ShipDefs/WeaponDefs source of truth, delete the numbers from prose, and have the docs reference the module. The doc already prescribes this pattern in its content pipeline ('수치 하드코딩 금지 → ShipDefs / WeaponDefs 모듈'); apply it to the design documents themselves before writing code.

## 🚫 The non-Server-Authority fallback puts hull kinematics on the helmsman's client while shipping PvP with cargo stakes — contradicting the document's own exploit analysis.
**실패 시나리오**: Ship doc §5.1 chooses kinematic specifically because '클라이언트가 선체를 소유하지 않으므로 텔레포트·Inf 속도·플링 익스플로잇 표면이 사라진다.' But roadmap gate D0's non-adoption branch is '함선 운동학은 조타수 클라이언트 소유 + 예측.' Combined with a deliberately generous hit tolerance (hull length × 0.15 + 12 studs) and PvP tiers staking 30–100% of cargo, that fallback is unshippable without exactly the custom anti-cheat the plan assumes it will not need. This is a solo developer signing up to fight cheaters in a stakes-bearing PvP game with client-owned movement.

**처방**: Make client-owned hull kinematics an unconditional non-option, independent of the Server Authority decision. Then cut PvP from v1 entirely (below), which removes the stakes and defers the whole question until there is an audience to cheat against.

## 🚫 Live-ops cadence is committed at 3–6x the developer's total capacity, and the season pass converts that overdraft into an obligation to strangers who paid.
**실패 시나리오**: The doc states live-ops is a permanent 1–1.75 FTE commitment. At 12 h/week the developer has 0.3 FTE — total, including all bug fixing and feature work. Naming the contradiction ('라이브옵스는 출시 작업이 아니라 영구 1–1.75 FTE 약정') is not resolving it, and the cadence is scheduled anyway. It is also internally inconsistent: '주간 신규 2 SKU' is 8–9/month, the very top of the stated '월 4~8 SKU' capacity, forever, with zero weeks off — and the 0.5–4 h/SKU costing is a professional artist's rate, not a first-timer's (realistically 6–20 h). Collapse order: weekly rotation breaks within 3–4 weeks of launch; season 2 slips, which is the reputational break because pass buyers churn on a broken cadence and leave 'dead game' reviews; bug response degrades concurrently; the quarterly major update never happens.

**처방**: Do not sell a season pass in v1. Ship a small PERMANENT cosmetic catalog — no rotation, no expiry, no seasons, ~3 SKUs at launch. A permanent catalog creates zero cadence obligation; a pass creates a contractual one at 3–6x capacity. Add seasons only when revenue funds a contract artist, and gate that on a real CCU number rather than a calendar.

## 🚫 No DataStore schema or migration plan for a large, weekly-changing persistent state.
**실패 시나리오**: v1 as written persists N owned hulls × 56 module unlock steps × per-hull fitting × cosmetic entitlements × towing/repair states × officer records with morale/loyalty/injury timers × deed counters × pity counters × season progress × infamy. The developer's shipped experience is 4 scalars in one key. Save corruption and lost progress from a schema change is a top-3 practical risk for a solo developer iterating weekly on persistent state, and the document — which is otherwise meticulous about engine constraints — never mentions versioning, migration, or backup once.

**처방**: Keep v1 persistence to one key with a version integer and a handful of scalars, and write the migration function before the second field is added. This is also a strong independent argument for the leaner v1: most of the schema disappears with the cut systems.

## ✂️ 컷 권고
- Crew/officer system — ENTIRELY. 6 stations, 24 mostly-two-sided traits, trait evolution by play history, layered portraits (52 parts / 92k combos), 240×180×6 name generator, ~200 barks, morale + loyalty + wage withholding, 4 injury states on real-time offline timers, port training with offline progress, 2 equipment slots, 12 unique officers with their own quests and unique ship abilities, veteran retrofit blueprints monthly, the ledger UI, and the take-over/assist rule. 400–800 hours to deliver, by its own hard cap, ≤15% of combat power. The worst cost-to-impact ratio in the document. Keep only the decorative deck NPCs that react to sail state — they are already paid for inside the juice bundle.
- Job advancement tree — CUT, not deferred to season 2. 4 classes → 8 branches → 8 capstones × 3 faction namings, ~36 distinct abilities each needing VFX + server validation + cooldown UI + a mobile button + balance, 40 deed counters, the Commission Warrant economy, respec with node graying, and a 14-second investiture ceremony with 6 officers delivering unique lines, avatar accessory attachment, sail-emblem dissolve, a commissioned 8-second shanty variant, and three faction locations built. The doc's own validation note admits 2 weeks per capstone is the danger line; at realistic solo pace it is 2–4 weeks each, so 4–8 months for the tier alone.
- Hull tiers 7 → 1 (arcade v1) → 2 (v1-B). The T2-is-fastest teaching device and the T5 three-way sidegrade endgame are genuinely elegant design, but they are designed for a game that has an endgame population. Each hull is also a mesh, a part budget, hand-authored collision boxes, a stat row, and a re-validation pass on every movement and cosmetic system.
- Module system: 14 modules × 4 tiers = 56 purchase steps → one upgrade line. The account-unlock / hull-cap two-axis structure is the smartest economy idea in the document and should survive on file — but 56 steps is progression content for a 31–40 hour curve that nobody has yet earned the right to build. The doc's own validation test (session당 1–2회 구매) cannot even be run without an audience.
- Boarding melee arena, 6 secondary objectives, the separate 4-button melee control set, and 3 arena layouts. The 6 objectives are the specific trap: fuse timer, mast climbing, a single duelist boss, two-point co-op interaction, escort, and rhythm input are six bespoke mini-games, and the melee layer is a second game with its own animations, hitreg, and mobile controls. 200–400 hours. Replace with a 2-second capture animation plus the reward-choice panel: preserves the emotional beat at ~2% of cost and TESTS WHETHER PLAYERS WANT TO CAPTURE before building the capture game. Keep the instanced-arena architecture decision on file — it is correct — for when it is actually built.
- Weapons 7 → 1 (broadside roundshot) + swivel gun. Mortar (world-space impact circle, 3.5s flight prediction, its own drag-to-place mobile UI), chase guns, stern powder barrels, heavy shot, and ram each carry an aim UI, a mobile control, VFX, server validation, and a balance surface. The three-axis distance × arc × scarcity RPS matrix is good design that requires roughly 4x the weapon count merely to exist — and it also requires the 6 enemy archetypes built to keep each weapon alive.
- Season pass and the 8-week season cadence and the weekly 2-new-SKU rotation. A pass is a contractual promise of a cadence running at 3–6x the developer's total capacity; breaking it is strictly worse than never selling it, because it converts silence into a betrayal and 'dead game' reviews. Replace with a small permanent catalog.
- PvP three-tier system: letters of marque with 90s lowering, infamy with 3 stages plus NPC navy pursuit fleets plus server-wide bounty display, power brackets (hull ±1 tier AND infamy band, cross-bracket damage 0), black waters with tickets and voyage-dividend settlement, insurance 3/day, revenge contracts at 150% recovery with 72h validity, repeat-hunt nullification. Every rule is a server-authoritative state machine with its own abuse surface, built for content the doc's own risk table warns may see <8% participation. Ship PvE only.
- Fleet passive trade routes, 10 berth slots, patrol risk-reduction interactions, fortress→regional-multiplier coupling, and the 3D dry-dock rotatable-miniature card grid. These are retention mechanics for a game that has retention, and they carry most of the persistence schema that creates the save-migration risk.
- Fortress assaults (10–15 min), kraken, and 3-phase 4-player legendary ship raids. Top-of-funnel content for a funnel that does not exist. The 4-player requirement also contradicts the plan's own rule that all content must be soloable and that difficulty is always tuned to solo.
- UGC emblem program Phase 2, custom free-text nameplates, the $4.99 subscription, festival tickets, the Voyage Credits second currency, and day-one regional pricing. Each is a support, moderation, or finance surface with recurring cost. Three fixed SKUs (3 R$ sail dye, 49 R$ emblem, 99 R$ sail set) is fully sufficient to learn whether this audience pays for ship cosmetics at all.
- Deck free-roam walking. Station seats plus 1-tap switching. Deletes the hardest engineering in the project and its permanent per-hull maintenance tax; the design doc already ranks it 스코프 컷 1순위 and suspects the replacement is better on mobile.
- Four currencies plus the 14 sealed blueprints gated behind wreck diving and treasure maps. One currency for v1. Note the internal contradiction being cut: blueprints are the sole key to T4 and require diving, while the exclusion table permanently excludes diving as 'a whole new character controller.' As written, the top of the upgrade tree is gated behind a feature the plan says it will never build.
- Ship doc §7's 12-week 구현 순서 table and §6.5's v1 fleet definition. These describe a second, much larger v1 (T2, T3, 56-step module system, cosmetics, dry dock, mortar, ram, fireship, towing, insurance, revenge) that contradicts the roadmap's vertical slice. Leaving both in the document guarantees they will be used to justify scope creep later. Delete outright.

## 🏛️ 반드시 지킬 것
- The deterministic Gerstner ocean as a pure GetHeight(x,z,t) function with 0-byte replication and a server/client parity harness. This is the actual technical moat, it is achievable, and buoyancy, rogue waves, list/sinking, and dry walkable gun decks all hang off it. It is also the one asset with resale value if the project dies (the doc's own Creator Store recovery path).
- The sail state machine as a global state machine driving 6 simultaneous feedback channels (camera FOV/distance/shake, spray rate, wind SFX, crew animation, rigging creak, edge vignette). Highest perceived-production-value per hour in the entire document. Ship it intact and unabridged even in the smallest version.
- Brace with the muzzle-glow telegraph and the 0.25s perfect window. Near-zero implementation cost (emissive swap + a server-timestamped flag), converts an HP race into a duel, and genuinely unoccupied on the platform.
- The weak point → swivel gun precision loop. The skill-expression axis, ~+32% effective DPS for mastery, cheap to build, and the doc is right that it must be taught in the first 30 minutes.
- '0 HP = a decision, not a death' plus the loss floor: cargo only, never hull/upgrades/cosmetics/blueprints; sinking is towing, not destruction; grounding costs time not assets. Correctly derived from the audience research and costs nothing to honor.
- No damage numbers — damage expressed only as debris, list, smoke, and speed loss. Protects the +0.2–1.4s flight-time dopamine window that the design correctly identifies as the core of the combat feel.
- The spyglass pre-revealing the cargo manifest BEFORE the engagement. The document is right that this is its best cost-to-effect item: it makes loot a goal to defend rather than a drop to receive.
- Every engine-risk avoidance decision, without exception: raycast + PartCache projectiles instead of physics parts, no cross-network-owner collision, ram and boarding as state transitions rather than physics, ModelStreamingMode = Atomic with ReplicationFocus on the hull root (and no extra focuses), zero unanchored gameplay-critical parts, no PreciseConvexDecomposition, playfield centered on the origin, depth as a texture field lookup rather than terrain physics. This engine-constraint mapping is better than most funded studio plans and is the reason the project is possible at all.
- Accessibility toggles (shake / sway / motion blur / spray) independently switchable from day one.
- The process discipline: PerfHUD built before any gameplay, real-device-only evidence with Studio framerate explicitly inadmissible, every session ends in something visible, one commit plus one clip per session, and the Friday 90-minute tester slot fixed in the calendar from W1.
- The monetization firewall in full: never sell power, competitive information, or safety; the SKU approval decision tree; the R1–R4 cosmetic-harmlessness rules (identical collision volume, readability layers force-rendered above skins, albedo floor 0.25, identical SFX); no paid random items; fast travel disabled while cargo is aboard.
- The pre-committed diagnosis rule: weak revenue below break-even CCU is BY DEFINITION a player-count problem and never a reason to sell power. This is the single best line in the document and the cheapest risk management in it. Keep it verbatim.
- The kill criteria and the named asset-recovery paths (arcade repackage, Creator Store ocean/ship kit) — re-indexed to calendar time and stranger data rather than fictional week numbers.
- Opt-in-only PvP as a PRINCIPLE: default off, permanent assets never at risk, clan membership never force-enables PvP. Keep the principle in the design; cut the three-tier implementation from v1.
