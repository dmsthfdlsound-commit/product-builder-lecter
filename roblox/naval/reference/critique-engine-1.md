# 적대적 검증: 엔진 (1차)

> Roblox engine reality check — physics/replication authority, moving-deck character simulation, StreamingEnabled behavior with large moving assemblies, low-end mobile render/memory budget, float precision at map scale, and whether the stated numbers are internally consistent. Verified against Roblox creator-docs and devforum bug/support threads rather than the doc's own assumptions.

**판정: needs-rework**

## 🚫 S1's core architecture — 'server sets hull CFrame at 20Hz, client interpolates' — is not implementable as written. You cannot control Roblox's replication rate for CFrame property writes, and there is no legal place for the interpolated position to live.
**실패 시나리오**: Two forks, both broken. (a) If the client interpolates the REAL hull part, the client hull and the server hull are at different world positions — up to 25 studs apart at gear3 (102 studs/s x 250ms). Every server-authoritative check (cannonball raycast, weakpoint hit, boarding range, rogue-wave alignment) then resolves against a hull the player cannot see. (b) If the client interpolates a visual CLONE and leaves the real collidable hull at the server position, players stand on an invisible hull offset from the visual one and appear to walk on water. Separately, moving a multi-part ship model by writing CFrames server-side is a documented bandwidth cliff — a CFrame is ~20 bytes and Roblox docs explicitly warn against CFraming many parts at once; a 150-part frigate x 16 ships x 20Hz is tens of thousands of transform updates per second and will saturate the per-client network budget long before the physics budget.

**처방**: Invert the authority model and lock it in session 0-2, not later. The server keeps NO ship geometry in Workspace — only an authoritative state table per ship (position Vector3, heading, gear, hp, segment). Broadcast that as a packed buffer over ONE UnreliableRemoteEvent at 15-20Hz (payload cap is ~908 bytes and >1000 bytes is dropped, so pack to ~16-20 bytes/ship: quantize position to 0.25 stud int32, heading to uint16, gear+hp to one byte each — 16 ships fits in ~320 bytes). Each client assembles its own ship models from ShipSpec locally and interpolates them freely. Server-side hit resolution runs analytically against ship-local hitbox capsules derived from the state table — never against parts. This simultaneously fixes the bandwidth cliff, the streaming bugs (blocker 3), and the LOD problem, because the server never owns a part at all.

## 🚫 Server authority + client interpolation means 250ms steering delay on the exact mechanic S5 declares the project's kill switch — and S5 is scheduled as a local, zero-latency test.
**실패 시나리오**: The doc says 'client interpolates' (보간), not predicts. Interpolation is definitionally behind the server. Session 0-4 builds S5 (gears, camera, audio) with no netcode; the 7-tester 3-minute handle test then passes on a build where gear input is instantaneous. In P2, once the server owns the transform, the same gear press takes ~250ms round trip to visibly change the ship. Asymmetric ramps of 1.2s accel / 0.6s decel will mask this in accel but NOT in the turn — a rudder input that responds a quarter-second late is the classic 'controls feel broken' complaint, which is literally the failure signal their own W4-2 wind A/B test is designed to detect. You will pass the kill-switch gate in W0 and fail it invisibly in W5, six weeks after freezing the backlog.

**처방**: Make the local player's own ship client-predicted, not interpolated: client simulates its own hull from its own input immediately, sends input intent (gear + rudder) to the server, server simulates the same deterministic model and sends back authoritative state; client soft-corrects over ~200ms toward the server state and hard-snaps only past a 6-stud threshold. Only OTHER ships are interpolated. Then re-run S5 with Studio's IncomingReplicationLag at 250ms as a mandatory pass condition. Note that IncomingReplicationLag delays server-to-client only — it does not reproduce the client-to-server leg — so also test on a real published place with a genuinely distant test device before believing the S5 result.

## 🚫 StreamingEnabled and player ships are actively incompatible in the way the doc uses them. The doc turns streaming ON at radius 1000 in S3 and treats it as a tuning knob.
**실패 시나리오**: Vehicles-under-streaming is a long-standing, still-open class of engine bug: parts welded to a chassis fail to stream out with it, players see frozen deformed ghost vehicles split into pieces, and objects that streamed out sometimes never stream back in. Concretely: two player ships pass at 400 studs closing speed, ship B crosses A's streaming boundary mid-broadside, and A's client is left with a permanent frozen hull husk at the boundary that A keeps shooting at while the real B sails away. Second concrete failure: your boarding-arena fallback (option 2) teleports a character to an off-map arena — teleporting into an unstreamed region with >100ms ping drops the player through the floor, which is a documented bug, and your stated 1.5s transition budget is not enough to RequestStreamAroundAsync a deck kit on a Galaxy A14.

**처방**: Ships must never be streamed instances. With the blocker-1 architecture they aren't (client-built, parented under a client-local folder, invisible to streaming entirely). Keep StreamingEnabled ON only for static content — ports, reefs, islands — with those set to ModelStreamingMode Atomic. Do not use Persistent for ships; docs describe Persistent as for rare cases with a small number of parts, and a ship whose part contents change (damage states, mast loss) is explicitly the case docs warn against. For the boarding arena, pre-build it at session start as a client-local model (no streaming involved) and budget the transition at 3-5s covered by a camera move, not 1.5s.

## 🚫 The gear table is geometrically self-contradictory with the weapon ranges. Gears 2 and 3 cannot fight, and one of the kill-criteria pivots is impossible.
**실패 시나리오**: Turn radius = v/omega. Gear1: 33/(18 deg/s) = 105 studs. Gear2: 60/(10 deg/s) = 344 studs. Gear3: 102/(5.5 deg/s) = 1063 studs. Broadside max range is 320 studs. So at gear2 your own turn circle radius (344) is LARGER than your gun range — you physically cannot circle a target and hold a broadside line, which is exactly the behavior you specify for the enemy AI state 'broadside line maintain' in session 5-5. At gear3 a single 360 takes 65 seconds and sweeps a 2100-stud circle. Net effect: the '4 gears' pitch collapses to 2 travel gears and 2 combat gears (0 and 1), and the 3-minute handle test in S5 exercises only the travel gears — it tells you nothing about combat handling. Worse, kill-criterion 3's fallback is a 400x400 stud arena: gear2's turn diameter is 688 studs and gear3 crosses the whole arena in 3.9 seconds. Your escape hatch does not fit the vehicle.

**처방**: Do the arithmetic before W0, not in W5. Either raise turn rates so every combat gear's turn radius sits inside broadside range (gear2 needs >=11 deg/s at 60 studs/s to hit 312 studs; realistically set gear2 to 60 studs/s / 14 deg/s = 245 stud radius), or explicitly redesign gear2/3 as no-fire travel modes and say so in the doc so you stop budgeting combat tuning for them. Resize the arena pivot to 1600x1600 studs minimum, or make the arena pivot gear-capped at gear1.

## 🚫 'Cosmetic roll/pitch computed client-only' breaks server-authoritative weakpoint hit registration — and weakpoints are the game's stated identity clip.
**실패 시나리오**: WeakPoints are attachment names on the hull (rudder, powder, mainmast). If the hull's roll/pitch exists only on the client, the client renders the powder magazine displaced by the roll while the server's hitbox is unrolled. On a 120-stud frigate at +/-8 degrees roll, a mast-height attachment displaces several studs laterally and vertically. Concrete: the player lines up the swivel gun on the glowing orange weakpoint, fires, sees the tracer pass through it, and the server reports a miss. That is the 'chip-chip-POP-snipe' 4-second clip the doc calls the game's identity, and it will register as a miss roughly whenever the ship is at wave peak or trough.

**처방**: Roll/pitch cannot be client-only. Make it fully deterministic from the shared WaveEval and a synchronized clock: roll = f(WaveEval(x,z,t)) with t = Workspace:GetServerTimeNow(), evaluated identically on server and client, so the server can reconstruct the exact hull orientation at any timestamp. Then resolve weakpoint hits in HULL-LOCAL space against fixed offsets and rotate into world using the reconstructed orientation at the shot's server timestamp. This also gives you free lag compensation. If you refuse this, the alternative is to make weakpoints non-positional (a HUD-targeted ability with a 0.4s lock, no geometry), but then delete the 'aim at the glowing bit' fantasy from the doc honestly instead of discovering it in W5.

## 🚫 Crew count is a mobile framerate suicide pact. 8-14 animated crew per ship, 5 animation states, across 4 player ships + 8 near AI ships.
**실패 시나리오**: Worst-case near-field is roughly 4x14 + 4x8 = ~88 animated rigs, plus 8 player characters. Community measurement puts ~100 humanoids firmly in 'requires aggressive optimization' territory, and Roblox's own guidance is that characters are very expensive to render in quantity in a small space — which a deck is, by definition. On a Galaxy A14 targeting 45fps, crew alone will eat the entire frame budget before the ocean, 60+ cannonball trails, and 12 hulls are drawn. And W2 is spent building this system before S3-style measurement is repeated, so you'll build it, film the rope-hauling clip, and then delete two thirds of it.

**처방**: Hard-cap animated rigs at 20 in the whole scene, enforced in code: animated crew ONLY on the local player's ship and the single nearest enemy within 200 studs. Beyond that, crew are static posed MeshParts (no Humanoid, no Animator) swapped between 3 poses on state change; beyond 400 studs, crew are deleted and replaced by a single billboard. Use Humanoid+Animator rather than AnimationController for the ones you do animate (measured significantly faster). Also: crew must not be Humanoids standing on the deck — see blocker 7.

## 🚫 NPC crew and player characters standing on a CFrame-driven deck will slide off. This is the single best-documented failure mode in the space and the doc's S2 spends 30 minutes 'trying' the version that is already known dead.
**실패 시나리오**: A part moved by CFrame writes has no assembly velocity, so friction transfers nothing to a standing Humanoid — the deck is teleported out from under the character each step. Devforum threads describe exactly this for CFrame-driven boats ('players glitch out and move off the ship'), and there is a filed engine bug that a Humanoid's AssemblyLinearVelocity does not inherit its platform's velocity when the platform is server-owned and the character is client-owned. Your ships move at 33-102 studs/s. A character will be left behind within one frame. Option 3 in S2 is not a control group, it is a known result.

**처방**: Cut S2's three-way bake-off and commit to option 1 (anchor both hulls during boarding) now — you already identified it as the recommended path, and the other two are pre-decided: option 3 is dead by engine behavior, option 2 has the streaming-teleport bug from blocker 3. That saves a session. For crew: never make them Humanoids. Crew are WeldConstraint-attached rigs (or just parts parented into the ship model) driven by animation tracks — they inherit the hull transform by construction and cost nothing in physics. For the anchored-boarding illusion: terrain water CANNOT be made to scroll or undulate (max terrain wave height is 1 stud), so 'animate the sea' is not available. SkyboxOrientation now exists so sky rotation is possible, but the honest and cheaper framing is 'grappled together, dead in the water' — freeze everything and don't fake motion.

## 🚫 Section 6 specifies 'Roblox Terrain Water + Gerstner cosmetic' as the water solution. These two cannot coexist.
**실패 시나리오**: Terrain water is a fixed voxel plane whose maximum wave height is 1 stud; it cannot be displaced by a Gerstner function. What you will actually ship is a flat terrain-water plane plus a separate translucent Gerstner mesh above it, producing two visible waterlines, z-fighting where they intersect, and ships that visually ride 6 studs above the 'real' water. Terrain water also forces Humanoids into the Swimming state and its reflection pass is a measurable GPU cost on low-end Android. Since your ships are kinematic and never actually float, terrain water buys you literally nothing and costs you the frame budget.

**처방**: Delete terrain water entirely. Ship a single camera-locked ocean plane: one large MeshPart (or a modest grid of skinned/EditableMesh tiles) parented to the camera in XZ, with scrolling UVs plus vertex displacement from the same WaveEval used by gameplay, so visual and logical wave height are the same function by construction. Falling in the water is a scripted respawn-to-deck, not a swim state. Add this to section 6's 'do not hand-build' table as 'terrain water — do not use'.

## 🚫 Anti-cheat as scoped is unbuildable, because character world position is client-replicated and legitimately moves at 102 studs/s plus wave heave.
**실패 시나리오**: Roblox replicates the local character's CFrame from the client. Any world-space speed or teleport check must tolerate ship speed (up to ~102 studs/s), rogue-wave heave, and 250ms of jitter — which means the tolerance window is wide enough that a speed exploiter standing on a deck is undetectable, and any window tight enough to catch them will false-positive constantly (a well-documented anti-exploit failure pattern). The doc's AntiCheat/'position validation' line assumes a stationary world.

**처방**: Never validate character position in world space. Validate it in SHIP-LOCAL space: reconstruct the hull CFrame server-side (which blocker 5's deterministic wave gives you for free), transform the character position into hull space, and check it against a deck AABB plus a local-space speed cap of ~24 studs/s. Off-ship world-space checks then only need to run during the anchored boarding phase, where the world is static and the checks actually work. Additionally, make character world position affect NOTHING except anchored-phase melee — all rewards, damage, and economy derive from server-computed ship state, so there is nothing for a position exploit to buy.

## 🚫 200 concurrent cannonballs with Beam/Trail visuals will not hold 45fps on a Galaxy A14, and the mortar netcode PASS criterion is arithmetically unreachable.
**실패 시나리오**: Beams and Trails are transparent textured ribbons — they cannot be batched with opaque geometry, they force sorting, and they generate overdraw. Practical mobile guidance lands around 150-300 total active particles and under 1000 draw calls / 1M triangles for the whole frame; 200 trails is 200 unbatchable draw calls before you have drawn a single hull. Separately, S4: a 3.5s mortar flight at a target moving 102 studs/s means the target travels 357 studs in flight, while the client is aiming at a target position that is ~250ms (up to 25 studs) stale. Roblox has no built-in lag compensation. The stated PASS of 'server impact within 3 studs of the client's predicted circle in 18 of 20 trials' cannot be met by prediction alone. And fallback (b), an 18-stud-radius AoE, makes a 36-stud-wide splash against a 30-60 stud ship — that is a guaranteed hit, which deletes the skill shot the mortar exists to be.

**처방**: Cannonballs: no Trail, no Beam, no ParticleEmitter per shot. One pooled opaque MeshPart with a baked streak texture, all sharing one MeshId+TextureId so they batch into a single draw call; spawn visuals only within 250 studs of the camera and represent everything farther as muzzle flash + splash only (a cannonball is not visible at 300 studs anyway). Cap concurrent visuals at 60 from day one — stop treating 200 as the target and 60 as the fallback. Mortar: redesign it as a ground-targeted ability, not a lead shot. The player places a marker on a water position, the marker is server-authoritative from the moment of placement (zero prediction error by construction), and the target dodges it by changing gear during the 3.5s flight. That makes it latency-immune, keeps it a genuine skill/counter-skill exchange, and lets you keep the 3.5s flight time you want dramatically.

## 🚫 The 700MB client memory budget is probably below Roblox's own mobile floor, so the metric will read as a permanent failure and you will chase it forever.
**실패 시나리오**: Reported mobile clients commonly sit around 900-1500MB even for modest experiences, with mobile using roughly 2x the memory of PC for the same content; developers routinely report ~1GB baseline. Setting a 700MB absolute ceiling means S3 fails on an empty baseplate, which will either make you distrust the metric or make you cut real content chasing an unreachable number.

**처방**: Replace the absolute number with a delta and a real signal: measure baseline memory on the target device with an empty place, then budget content at baseline + 350MB, tracked per Developer Console category (GraphicsTexture, GraphicsMeshParts, PhysicsParts) so you know WHAT grew. For the actual pass/fail, use Roblox's low-end Android crash-rate analytics as the gate rather than a memory number, and keep the 1024 texture cap you already specified. Also add a 20-minute soak to the Friday device test specifically to catch GraphicsParts-category leaks, which have been reported to grow by gigabytes over 20-30 minutes.

## 🚫 Three regions plus travel time implies a map far enough from origin to hit float32 precision, and the doc never states a map size or coordinate budget.
**실패 시나리오**: Vector3 is single-precision. Physics instability, jitter, vibrating parts, and inconsistent collisions are reported starting in the ~20,000 stud range from origin, with severe reports around a map built at +/-20,000. Concrete: your southern region sits 30,000 studs out, and the boarding deck — the one place in the game with real character physics and precise footing — jitters and the 'zero fall-through in 10 trials' S2 result you measured near origin does not reproduce there. S1's 30-minute drift test will also read differently at 30k than at 0.

**처방**: Write a coordinate budget into the W0 architecture decisions: total playable extent <= 16,000 studs across, centered on origin (so no point exceeds ~8,000 studs). Three regions become three sectors of one 16k box with different spawn tables and difficulty, not three geographically distant landmasses — the doc already says regions are 'difficulty gradient, no locks', so nothing is lost. Travel time comes from speed, not distance: at gear3 (102 studs/s) crossing 8,000 studs is already 78 seconds, which is plenty. Run the S1 30-minute drift test at (7500, 0, 7500), not at origin. Boarding arenas go near origin, always.

## 🚫 W0's spike ordering is backwards relative to the doc's own risk ranking, and S2's result feeds a decision S1 already locked.
**실패 시나리오**: S2 is labeled 최고 위험 and its outcome determines whether characters ever occupy ship-local space — which determines the coordinate system and hitbox model that S1 (session 0-2) commits to. The flowchart runs S2 last, in session 0-7, after S1, S3 and S4 have all built on S1's choice. If S2 lands at L1 (anchored boarding), you want hull-local transforms and deterministic wave reconstruction everywhere; if it lands at L3 (cutscene), you can skip all of that. Discovering that in session 0-7 means sessions 0-2 through 0-6 were built on a coin flip.

**처방**: Reorder to S5 -> S2 -> S1 -> S3 -> S4. S2 in its stripped form (option 1 only, per blocker 7) is a half-session, not two sessions, because you are no longer running a bake-off. Run it second, immediately after the S5 kill switch, so the architecture decisions in S1 are made with the boarding answer in hand. Also: AnalyticsService funnel events only fire from the server in PUBLISHED experiences, not from Studio and not from the client — so 'instrument from the first line of code' needs a published staging place in session 0-1, or your funnel code is untested until P3.

## ✂️ 컷 권고
- Terrain water — cut entirely, not tuned. It cannot be displaced (max wave height 1 stud), it conflicts with the Gerstner plan, it forces Humanoid swim state, and its reflection pass costs GPU you do not have. Replace with a camera-locked mesh ocean driven by the same WaveEval. (blocker 8)
- S2's three-way bake-off — cut options 2 and 3. Option 3 (pure physics deck) is dead by documented engine behavior; option 2 (arena teleport) carries the streaming teleport fall-through bug. Build option 1 only. Saves ~1.5 sessions. (blocker 7)
- S3's 'control group physics-part cannonball version' — cut. You already know the answer, and running it costs a measurement session to confirm a foregone conclusion. Spend that time on the pooled-opaque-streak implementation instead.
- 200 concurrent cannonballs as a target — cut to a 60 hard cap from day one. Stop framing 60 as the fallback; it is the design. Same for 8 AI ships (not 12), single-part silhouettes beyond 250 studs (not conditionally), and 8-player servers. These four 'fallbacks' are the actual specification; committing now removes an entire measurement session and prevents building content that only works at the aspirational numbers. (blocker 10)
- Crew on non-local ships — cut animated crew to the player's ship plus one nearest enemy, cap 20 animated rigs total, static posed meshes beyond that. The rope-hauling clip only needs the local ship. (blocker 6)
- Geographically distant regions — cut. Three sectors of one 16k-stud origin-centered box, differentiated by spawn tables and palette, not by distance. The doc already says no locks and difficulty gradient only, so this costs nothing and buys you out of float precision hell. (blocker 12)
- Mortar as a predicted lead shot — cut and replace with a ground-targeted water marker. Keeps the 3.5s drama, removes the unwinnable netcode problem, and stays a real skill exchange (which the 18-stud AoE fallback would not). (blocker 10)
- Gear 2 and 3 as combat gears — cut from the combat design and label them travel-only, OR fix the turn rates. Right now gear2's turn radius (344 studs) exceeds broadside range (320), so the enemy AI's 'maintain broadside line' state is impossible to execute. Pick one; do not ship the contradiction. (blocker 4)
- The 400x400 stud arena pivot — cut or resize to 1600x1600. Gear2's turn circle is 688 studs across; the escape hatch does not fit the ship. (blocker 4)
- 'Cosmetic client-only roll/pitch' — cut the phrase. Roll must be deterministic and server-reconstructable or weakpoint sniping does not register. (blocker 5)
- TestEZ — minor, but prefer jest-lua/jest-roblox. Roblox uses Jest internally and provides a TestEZ migration guide; starting a 7-month project on the older harness is avoidable churn.
- The 700MB absolute memory ceiling — cut as a gate. Mobile Roblox commonly baselines near or above it. Replace with baseline + 350MB tracked per Developer Console category, and gate on low-end Android crash rate instead. (blocker 11)

## 🏛️ 반드시 지킬 것
- Week 0 spike-before-build discipline with written PASS numbers and pre-committed fallbacks. This is the single thing that most saves this project, and it is unusual to see it written down honestly. Do not let the blockers above become an excuse to skip it.
- Pre-documented kill criteria with numeric thresholds and a stated pivot target. The sunk-cost tripwire is the correct instinct.
- S5 as the gate before anything else exists — 'no combat code, does the boat feel good' is exactly right for this genre. It just has to be tested under 250ms latency (blocker 2).
- Real low-end Android + iPhone SE2 as the measurement device, with Studio numbers explicitly disallowed as evidence. Non-negotiable, keep it.
- Ban on Toolbox models containing Scripts, plus a CI scan for Script/RemoteEvent after mesh import. This is a genuine backdoor kill and most solo devs skip it.
- Shallow power curve capped at 2.5x floor-to-ceiling. This is the design decision that makes a difficulty-gradient open sea possible at all; guard it against every later temptation.
- ShipSpec as data + runtime assembler, one base hull mesh scaled per class. Under the corrected architecture (blocker 1) this becomes MORE load-bearing, not less, because clients assemble ships locally from it.
- Shared analytic WaveEval(x,z,t) with raycasting explicitly forbidden. Correct call, and blocker 5 makes it the foundation of hit registration too.
- Rojo + git + CI from session 0-1 instead of pasting into Studio. At this scale this is not optional.
- Cosmetic-only monetization with an explicit no-power-sales rule, plus loss caps and insurance instead of full looting. Both are the right long-term calls.
- The visibility rule that maps invisible work to a mandatory clip — especially the translucent ghost-ship render for netcode. That ghost render is also the best debugging tool you will have for blockers 1 and 5; build it in session 0-1, not 0-3.
- WIP limit of 1 and the 3-session spike tripwire.
